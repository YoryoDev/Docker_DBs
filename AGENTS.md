# Repository guide

## Project model

- This is a Docker/Podman Compose configuration repository, not an application. Each engine directory is a standalone Compose project; root `compose.yaml` includes all seven projects.
- Root Compose loads every included `<engine>/.env` before profiles are selected, so even a one-profile root command requires all seven `.env` files. For focused work, use a standalone file. Docker helpers add `--project-directory`; Podman helpers intentionally omit it because `podman-compose` rejects that option and resolves relative paths from the absolute `-f` path.
- Root and standalone invocations create different Compose projects while reusing fixed container and named-volume names. Do not alternate modes for existing containers.
- `podman compose` is only a wrapper. Standalone projects require profiles and `depends_on.condition: service_completed_successfully`; Podman's root flow additionally requires a Docker Compose v2 provider because `podman-compose` 1.5 cannot parse `include` entries with per-project `env_file`. Do not remove init ordering to accommodate an incomplete provider.
- PostgreSQL 18 is the naming exception: directory/profile/container are `postgresql18`, but its Compose service key is `postgresql`.

## Safety and compatibility

- Never read, copy, print, or edit ignored `<engine>/.env` files; they contain local credentials. Use `.env.example` or the dummy fixtures generated by `tests/test_setup.py`.
- Do not start, stop, pull, recreate, or remove the user's Docker or Podman containers unless explicitly requested. Never run `down -v`: named data, log, and backup volumes are persistent state, and a root profile does not safely scope volume deletion to one engine.
- Docker and Podman have separate storage. Never switch runtime for an existing database and imply that its same-named volume or data carries over.
- Keep local defaults bound to `127.0.0.1`; `0.0.0.0` exposes a database on every interface.
- Container names, named-volume names/mounts, and engine initialization variables are compatibility boundaries. `test_persisted_identity_unchanged` compares them with `HEAD`; treat a failure as a migration requiring explicit user scope, not as a test to weaken.
- If helper behavior changes, keep `.bash_aliases`, `docker_dbs.fish`, and `DockerDBs.ps1` equivalent. Docker aliases are unprefixed; Podman mirrors use `pod-`. Both must preserve paths containing spaces, forward extra arguments, and return the runtime's exit status.
- Keep README tables and operational notes synchronized when changing image tags, ports, profiles, resource limits, mount paths, or supported commands.

## Verification

Run the safe checks; they do not start databases or read real `.env` files:

```sh
bash -n .bash_aliases
fish --no-config --no-execute docker_dbs.fish
python3 tests/test_setup.py
git diff --check
```

- Run one regression with `python3 tests/test_setup.py SetupTests.<test_name>` (for example, `SetupTests.test_compose_root_and_standalone`).
- The suite mocks Docker and Podman for shell helpers and uses temporary dummy credentials for Compose config. Runtime checks skip when their CLI is absent, Fish checks skip without Fish, and PowerShell checks skip without `pwsh`; inspect skipped tests before claiming full compatibility.
